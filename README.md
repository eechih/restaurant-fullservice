# 全服務餐廳 POS + KDS PoC

中大型全服務餐廳的 POS 與廚房顯示系統（KDS），使用 AWS Amplify Gen 2 + React。複製自 `restaurant-pos-kds`，改為先吃後付、內外場分工。計畫和設計見 [全服務餐廳 PoC 計畫](docs/full-service-plan.md)。

**內用流程：** 候位 → 帶位開桌 → 服務員點餐，直接送廚 → 各出餐站製作 → 出菜口整輪上菜 → 加點 → 請求結帳 → 櫃台收款（可拆帳）→ 待清理 → 已清理

**顧客掃碼點餐：** 掃桌上的 QR Code 點餐 → 服務員確認後才送廚，算進這桌的帳單

**訂位：** 櫃台登記電話訂位 → 當天和候位一起顯示 → 到店後帶位開桌

## 本機試用（不需要 AWS）

```bash
npm install
npm run dev
```

打開 http://localhost:5173 ，匯入範例資料。沒有 `amplify_outputs.json` 時，App 會進入**本機展示模式**：資料存在瀏覽器裡，只在同一個瀏覽器的分頁之間同步，也不需要登入。

右上角的「角色」可以切換身分，每個分頁各自記住。例如一個分頁選「廚房」看 `#/kds`，另一個選「服務員」點餐，再開一個選「主管」核准取消。顧客點餐頁可以從 `#/pos/qr` 的「開啟點餐頁」進入。

## 角色

一個帳號可以有多個角色（Cognito 群組）。後端的每個操作都依 `src/domain.ts` 的 `rolesFor()` 限定群組，畫面也用同一份表決定顯示什麼。

| 角色 | 群組 | 可以做的事 |
|---|---|---|
| 店長 | `MANAGER` | 全部，包括菜單、出餐站、桌位、QR Code、帳號、報表 |
| 主管 | `SUPERVISOR` | 現場的所有操作、核准取消和折扣、日結報表、出餐分析 |
| 櫃台 | `CASHIER` | 候位、訂位、帶位開桌、申請折扣、結帳收款、清桌 |
| 服務員 | `SERVER` | 開桌、點餐、確認掃碼點餐、申請取消和折扣、上菜、請求結帳、清桌 |
| 廚房 | `KITCHEN` | KDS、出菜口、售完管理 |

## 部署到 AWS

需要已設定好的 AWS 憑證。

```bash
npx ampx sandbox
```

這會建立一套個人開發用的 Cognito、AppSync 和 DynamoDB，並產生 `amplify_outputs.json`。App 偵測到這個檔案就會改用 AWS。

公開註冊已關閉，第一個帳號要由管理員建立，並加入店長群組。User Pool ID 在 `amplify_outputs.json` 的 `auth.user_pool_id`：

```bash
aws cognito-idp admin-create-user --user-pool-id <USER_POOL_ID> --username <EMAIL>
aws cognito-idp admin-add-user-to-group --user-pool-id <USER_POOL_ID> --username <EMAIL> --group-name MANAGER
```

Cognito 會寄送臨時密碼，第一次登入時要變更。之後的帳號由店長在「店務設定 → 員工帳號」邀請。

> **IAM 角色上限：** 這個專案大約需要 30 個 IAM 角色。AWS 帳號預設最多 1000 個，和其他專案共用時要留意，不夠時部署會失敗並回滾。見[全服務餐廳 PoC 計畫](docs/full-service-plan.md#aws-帳號的-iam-角色上限)。

> **注意：** 在 sandbox 新增或變更某張表的索引時，Amplify 會**重建那張表並清空資料**，而且預設沒有備份。正式部署不會這樣。

移除 sandbox 資源：

```bash
npx ampx sandbox delete
```

## 資料模型

| 模型 | 用途 | 誰寫入 |
|---|---|---|
| `DiningTable`、`Station`、`MenuCategory`、`MenuItem` | 桌位（含分區）、出餐站、菜單。分類有預設出餐站，品項可以另外指定，也可以設定不收服務費 | 店長；售完由廚房、主管切換 |
| `StoreSettings` | 店名、統編、地址、電話（印在收據上）和服務費率，只有一筆 | 店長 |
| `Seating` | 哪一桌有人，以 `tableId` 為主鍵。帳單結清後保留到按「已清理」，所以能分出待清理 | `orders` 函式 |
| `GuestCheck` | 一組客人的帳單：工作單、折扣、服務費率、小計、折扣、服務費、合計、已付金額、已付品項、狀態 | `orders` 函式 |
| `Order` | 一輪點單。服務員的直接送廚；顧客掃碼的先是待確認 | `orders` 函式 |
| `KitchenTicket` | 一輪在一個出餐站的工作單，ID 由點單和出餐站推導，記錄各狀態的時間 | `orders` 函式 |
| `LineVoid` | 品項取消的申請與核准，ID 是 `工作單#品項`，一個品項只有一筆 | `orders` 函式 |
| `Payment` | 一筆收款，記錄方式、金額、拆帳方式和發票資料（載具、統編、愛心碼） | `orders` 函式 |
| `WaitlistEntry` | 候位和訂位，訂位多了時間和備註 | `orders` 函式 |

幾個設計決定：

- **金額由伺服器決定：** 點餐只送品項和選項，收款只送拆帳方式，金額都由後端計算。帳單在每次送廚、取消、折扣後都由後端重新計算。前端算出的是預估，和伺服器不同時會被拒絕。
- **帳單不會算錯：** 送廚、核准取消、收款都在同一筆交易裡更新帳單，並以帳單上次更新的時間為條件。兩人同時操作時，後到的會重讀後重試。
- **重送不會重複：** 開桌、點單、收款和候位的 ID 由前端產生並在重試時沿用，網路失敗後重送不會多開一桌、多送一輪或多收一次。
- **品項快照：** 名稱、價格、選項和出餐站在送廚時就存進工作單，之後改菜單不影響既有帳單。
- **斷線補單：** App 在連線恢復時會重新載入完整資料，另外每 60 秒同步一次。畫面只保留較新的紀錄，延遲到達的舊通知不會蓋掉新狀態。

## 測試

```bash
npm test
npm run typecheck
```

測試透過本機展示模式的 Repository 執行完整流程，它和 Lambda 共用 `src/domain.ts` 的規則。Lambda 本身的 DynamoDB 交易只有型別檢查，要部署到 sandbox 才能驗證。

## PoC 的已知限制

- **權限收回有延遲：** 拿掉角色或停用帳號後，對方會在所有裝置被登出，但已開啟的畫面在登入憑證到期前（最長 1 小時）仍能操作。
- **沒有退款：** 開始收款後就不能取消品項。結帳後要退款只能在系統外處理。
- **電子發票尚未開立：** 只記錄載具、統編和愛心碼，要和加值中心簽約後才能串接。收據不是統一發票。
- **折扣和取消在收款後就不能改：** 會變成退款，目前沒有退款流程。
- **濫用防護：** 每桌最多 10 筆待確認的掃碼點餐，但沒有依來源限制請求頻率。公開上線前應再加 AWS WAF。
- **時間以裝置時鐘為準：** KDS 和出菜口的等待時間會受各裝置時鐘誤差影響。
- **取消只能取消整筆品項：** 要從 3 份改成 2 份時，需取消後重新點餐。
- **未送廚的點餐：** 只存在該裝置的記憶體，重新整理就會消失。
- **離線：** 斷線時不能送廚和收款，畫面會顯示連線狀態。
