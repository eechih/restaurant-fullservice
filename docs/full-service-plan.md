# 全服務餐廳 PoC 計畫

- **目標：** 中大型全服務餐廳的 POS + KDS，內外場分工明確
- **起點：** 複製自 `restaurant-pos-kds`（commit `906f478`），沿用 Amplify Gen 2 + React、TanStack Router/Query、Repository 架構
- **建立日期：** 2026-11-06
- **狀態：** 第一、二階段已實作（2026-11-06），尚未在 AWS 上驗證。第二階段的發票只記錄資料，尚未串接開立

## 和原 PoC 的差別

原 PoC 為小吃店設計：每一輪都先付款才送廚，帳號只分店長和員工。全服務餐廳的做法不同：

| | 原 PoC | 全服務餐廳 |
|---|---|---|
| 付款 | 每輪先付款才送廚 | **先吃後付**，離開前統一結帳，可拆帳 |
| 點餐的人 | 顧客掃碼或櫃台 | 主要是服務員，顧客掃碼為輔 |
| 角色 | 店長、員工 | 店長、主管、櫃台、服務員、廚房 |
| 廚房 | 一個 KDS 看全部 | 依出餐站分線，出菜口統整 |
| 桌況 | 空桌、用餐中 | 空桌、用餐中、**待清理**，加上候位 |

## 系統藍圖

業界成熟的餐廳系統分為前廳、後廚、後台三塊。這個 PoC 依序補齊：

| 系統 | 內容 | 階段 |
|---|---|---|
| POS | 點餐、桌位圖、先吃後付、拆帳結帳 | 1 |
| 角色與權限 | 依職務分權，取消要主管核准 | 1 |
| KDS | 依出餐站分線、出菜口、計時與超時警示 | 1 |
| 桌況與候位 | 待清理狀態、候位名單、帶位 | 1 |
| 發票與收據 | 電子發票、載具、統編、收據列印 | 2，正式營業前必做 |
| 服務費與折扣 | 一成服務費、折扣需主管核准 | 2 |
| 訂位 | 線上與電話訂位，和候位整合 | 2 |
| 出餐分析 | 記錄每道菜的製作時間，找出瓶頸 | 2 |
| 庫存 | 依食材用量（BOM）扣庫、安全庫存提醒、採購建議 | 3 |
| 排班與打卡（WFM） | 打卡、排班、勞基法檢查、營業額對工時 | 4 |
| 會員（CRM） | 用餐偏好、行銷推播 | 5 |
| 外送整合 | Uber Eats、Foodpanda 訂單進 POS | 5，需先和平台簽約 |

## 第一階段的設計

以下三點已於 2026-11-06 確認：顧客掃碼點的單要服務員確認後才送廚、取消已送廚的品項要主管核准、KDS 依出餐站拆單並設出菜口。

### 1. 先吃後付、桌邊結帳

- **送廚不必付款：** 服務員點的單直接送廚，每輪成為一張工作單，全部掛在這桌的帳單上。
- **顧客掃碼點餐：** 掃碼點的單先進「待確認」，服務員確認後才送廚。這樣可以防止惡作劇，也能擋下上一組客人留著的連結：直接送廚的話，舊連結點的菜會算到下一組客人的帳上。
- **結帳：** 客人要結帳時，服務員或櫃台開啟帳單，可以：
  - 整桌一次付清；
  - **依品項拆帳**：每個人勾自己點的；
  - **平均分攤**：分成 N 份。
  - 一張帳單可以有多筆付款，例如一部分現金、一部分刷卡。付清後桌子變成「待清理」。
- **帳單計算由後端負責：** 金額、拆帳、付款都在 Lambda 驗算，前端算的只是預估。
- **取消品項：** 結帳前取消，不需退款。已送廚的品項要主管核准，見下一節。

### 2. 角色與權限

一個帳號可以同時有多個角色（Cognito 群組）。

| 角色 | 可以做的事 |
|---|---|
| 店長 | 全部，包括菜單、桌位、帳號、報表 |
| 主管 | 現場調度、核准取消和折扣、看當日報表 |
| 櫃台 | 帶位、候位、結帳收款 |
| 服務員 | 開桌、點餐、確認顧客掃碼的單、上菜、請求結帳 |
| 廚房 | 只看 KDS，改製作狀態 |

- **主管核准：** 服務員取消已送廚的品項時，會送出一筆「取消申請」，主管在自己的裝置上核准或駁回。核准前，廚房畫面就會標示「申請取消中」。
- **畫面依角色調整：** 例如廚房帳號登入後只會看到 KDS。

### 3. KDS 分線

- **出餐站：** 店長設定出餐站，例如炒台、烤台、砧板、冷盤、飲料吧。每個分類指定一個預設站，個別品項可以另外指定。
- **依站拆單：** 送廚時，一輪點單會依品項拆成各站的工作單，每張有自己的狀態，各站只看自己的單。
- **出菜口（Expo）：** 另一個畫面依桌、依輪次彙整各站進度，全部完成才通知服務員上菜，避免同一桌的菜分批送出。

### 4. 桌況與帶位

- **桌況：** 空桌 → 用餐中 → 已結帳**待清理** → 撤桌人員按「已清理」→ 空桌。
- **候位名單：** 櫃台登記稱呼、人數、電話（選填），系統依人數提示適合的空桌。帶位時直接開桌。
- **桌位分區：** 桌位可以分區，例如一樓、二樓、包廂。之後可以把分區指派給服務員。

## 第一階段的實作

| 項目 | 做法 |
|---|---|
| 帳單一致性 | `GuestCheck` 記錄輪數、帳單合計、已付金額和已付品項。送廚、核准取消、收款都在同一筆 DynamoDB 交易裡，以帳單的 `updatedAt` 為條件更新它，所以兩人同時收款不會超收，剛送出的一輪也一定算進帳單 |
| 寫入路徑 | 桌況、點單、廚房、取消、收款、候位都只由 `orders` 函式寫入，回傳統一的 `LiveChange`，前端只訂閱 `onLiveChange` |
| 規則共用 | 計價、拆單、付款金額、取消條件寫在 `src/domain.ts`，Lambda 和本機展示模式共用 |
| 權限 | 每個操作在 schema 用 `rolesFor()` 限定 Cognito 群組；畫面用同一份表決定顯示哪些頁面和按鈕 |
| 拆帳 | 付清、依品項、平均分攤（剩餘金額除以剩餘人數，無條件進位）、自訂金額，可以混用。開始收款後就不能再取消品項，因為那會變成退款 |
| 取消品項 | 一個品項最多一筆申請。服務員送出後由主管核准或駁回，駁回後可以再申請；主管和店長自己取消時直接生效 |
| 展示模式 | 右上角可以切換角色，每個分頁各自記住，方便同時開廚房和外場 |

## 第二階段的實作

以下於 2026-11-06 確認：服務費以折扣後金額計算，可設定不收的品項；四種折扣都支援；發票先記錄資料，串接之後再做；訂位先做員工代訂。

| 項目 | 做法 |
|---|---|
| 服務費 | 店長在「店務設定 → 店家」設定費率，開桌時記在帳單上，之後改費率只影響新開的桌。品項可以設定不收服務費，送廚時記在工作單的品項上 |
| 折扣 | 整單打折、整單折抵、單品招待、單品打折或折抵。每個品項和整張帳單各最多一筆。服務員和櫃台送出申請，主管核准；主管和店長自己加的直接生效。和取消品項一樣，開始收款後就不能再改 |
| 帳單計算 | 先扣單品折扣，再扣整單折扣，再對剩下的、要收服務費的金額收服務費。後端每次都用一致讀取重算整張帳單（帳單上記有所有工作單的 ID），不靠累加 |
| 依品項拆帳 | 每個品項分攤到的整單折扣和服務費一併計入；四捨五入的零頭由付最後幾個品項的人付清 |
| 發票資料 | 每筆收款記錄載具（手機條碼、自然人憑證）、統編（含檢查碼）或愛心碼，`invoiceNumber` 先留空。簽約後在 `orders` 函式的 `recordPayment` 收款成功後開立並回填 |
| 收據 | `#/receipt/$checkId` 依 80mm 收據機排版，列出品項、折扣、服務費和每筆收款的發票資料，註明不是統一發票 |
| 出餐分析 | 工作單記下開始製作、完成、上菜的時間。「店務設定 → 出餐分析」依付清的帳單，按出餐站和菜色列出等待、製作、等待上菜的平均時間和最慢的工作單 |
| 訂位 | 和候位用同一個模型，訂位多了時間和備註。當天的訂位和候位一起顯示在外場，用同一個流程帶位；可以標記未到。帶位給現場客人時，會提醒接下來 2 小時的訂位 |

### 換桌與併桌（2026-11-06）

| 項目 | 做法 |
|---|---|
| 換桌 | 把帳單的其中一張桌移到空桌。還沒上的菜，工作單上的桌名會跟著改，廚房和出菜口送到新桌 |
| 一組客人坐多張桌 | 帳單記錄所有桌位（`tableIds`），桌名顯示成 A1+A2；任一張桌的 QR Code 點餐都進同一張帳單；取消開桌和結帳會一起處理所有桌 |
| 合併帳單 | 把另一桌的帳單併入：工作單、取消紀錄、單品折扣、桌位都移過來，人數相加，服務費率以併入的那桌為準；被併的帳單標為 `MERGED`。開始收款後不能合併；兩邊都有整單折扣時要先取消一個。全部在一筆交易內完成，超過 DynamoDB 單筆交易 100 個寫入時拒絕 |
| 權限 | 服務員、櫃台、主管、店長都能做，不需核准，因為金額不變 |

`tableIds` 是選填欄位：在這之前開的帳單沒有它，程式改用 `tableId`。後端已 commit，尚未部署到 sandbox。

### 分道上菜（2026-11-06）

| 項目 | 做法 |
|---|---|
| 道次 | 固定四道：立即、前菜、主菜、甜點。店長替分類設定預設道次，品項可以另外指定，服務員點餐時也可以改。沒設定的算「立即」，所以舊菜單的行為不變 |
| 送廚 | 「立即」的菜直接送廚。一組客人第一次點的菜中，道次最小的那一道也會一起送出；之後的道次先「待叫菜」（工作單狀態 `HELD`），仍然算在帳單上 |
| 叫菜 | 服務員按「叫主菜」，主菜和之前還沒叫的道次一起送廚，送廚時間從叫菜時開始算。之後加點的菜，道次已叫過的就直接送廚 |
| 畫面 | KDS 下方列出「等待叫菜，可以先備料」，不計時、不響提示音。出菜口按每一輪的每一道分開，那一道全部完成才通知上菜 |
| 顧客掃碼點餐 | 顧客不能選道次，一律用菜單的設定 |

### AWS 帳號的 IAM 角色上限

2026-11-06 第一次部署 sandbox 時失敗：這個帳號和其他專案共用，IAM 角色已有 952 個，上限是 1000。Amplify 會替每個由函式處理的操作各建一個資料來源和角色，第一階段就需要 49 個。

因此員工的操作改成每個函式共用一個 Lambda 資料來源（`backend.data.addLambdaDataSource`），用 `amplify/data/invokeFunction.js` 呼叫，角色從 27 個降到 5 個。顧客的三個操作開放給訪客，Amplify 的自訂 resolver 不支援，所以仍各用一個。之後帳號角色再增加時，要申請提高上限或清理不用的角色。

## 待決定

- **外帶：** 原 PoC 的外帶（先付款、取餐號、叫號螢幕）在第一階段移除。之後要做時，可以讓每筆外帶成為一張沒有桌位的帳單，沿用新的結帳流程。

- **電子發票串接：** 要選定加值中心（例如綠界、藍新）或財政部 Turnkey，簽約後才能開立。
- **顧客線上訂位：** 需要不必登入的訂位頁和防灌單機制。
- **QR Code 輪換：** 掃碼點的單要服務員確認，所以第一階段先不做每組客人換一次 QR Code。
- **離線：** 和原 PoC 一樣，斷線時不能送廚和結帳。
